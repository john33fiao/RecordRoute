# Rust Migration Roadmap (Backend)

> 목적: 과거의 "전면 Rust 전환 시도 후 리버트" 경험을 반복하지 않기 위해, **중단 가능/되돌리기 쉬운 단계적 마이그레이션** 전략을 정의한다.

## 0. 원칙 (실패 재발 방지)

- **Big-bang 금지**: Python 백엔드를 한 번에 교체하지 않는다.
- **병행 운영 우선**: 동일 API를 Python/Rust에서 동시에 검증한다.
- **계약(Contract) 고정 후 구현**: 기존 HTTP 계약(`/process`, `/search`, 에러 필드)부터 테스트로 고정한다.
- **관측성 선행**: 성능/에러/리소스 지표가 없으면 전환하지 않는다.
- **언제든 리버트 가능**: 라우팅 스위치(feature flag)로 즉시 Python 경로로 복귀 가능해야 한다.

---

## 1. 범위 정의 (무엇을 Rust로 옮길지)

### 1-1. 우선 전환 대상 (Low-risk)
- CPU 바운드이거나 독립 모듈 성격이 강한 영역
  - 검색 랭킹/스코어링 일부
  - 문서 메타데이터 전처리
  - 파일/경로 정규화 유틸리티 (계약 유지 전제)

### 1-2. 후순위 전환 대상 (High-risk)
- 워크플로우 오케스트레이션(`/process`), 큐/취소/진행상태 관리
- STT/교정/요약 모델 호출 및 외부 툴 체인 연계
- 업로드/레지스트리/히스토리의 쓰기 경로 전체

### 1-3. 비전환(당분간 유지)
- 프론트엔드(`frontend/src`)는 변경 최소화
- Python 기반 모델 연동은 Rust에서 래핑/호출 방식으로 병행 유지

## 3. Phase 1 — Sidecar PoC (3~4주)

목표: Python 서버는 유지하고, Rust 서비스를 **별도 프로세스(sidecar)** 로 붙여 일부 read-only 기능만 위임.

- p95 응답 시간 개선 또는 최소 동급
- 장애 시 Python 자동 폴백 가능

## 6. 테스트 전략 (항상)

- 계약 테스트: 기존 API 응답 필드/코드/정렬/페이징 일치
- 회귀 테스트: 기존 핵심 세트 지속 실행
  - `pytest tests/http_api/test_workflow.py`
  - `pytest tests/http_api/test_search.py`
  - `pytest tests/server/test_queue.py`
  - `pytest tests/test_vocab_system.py`
- 혼합 E2E 테스트
  - `BACKEND_ENGINE=python|hybrid|rust` 3모드 비교
- 성능 테스트
  - 고정 데이터셋 + 고정 시나리오로 주차별 추세 기록

## 7. 리스크 & 대응

- **API 드리프트**
  - 대응: 스냅샷/계약 테스트 + PR 체크 필수화
- **운영 복잡도 증가(이중 런타임)**
  - 대응: 사이드카 관측성/헬스체크/자동 폴백
- **팀 러닝커브**
  - 대응: Rust 코드 소유 구역 제한 + 코드리뷰 체크리스트
- **배포/빌드 지연**
  - 대응: 멀티스테이지 Docker 캐시 및 바이너리 아티팩트 전략

## 8. 추천 일정 (예시: 12주)

- 1~2주: 사전 준비/회고/기준선/테스트 고정

- 7~10주: Phase 2 하이브리드 canary
