# Rust Migration Roadmap (Backend)

> 목적: 과거의 "전면 Rust 전환 시도 후 리버트" 경험을 반복하지 않기 위해, **중단 가능/되돌리기 쉬운 단계적 마이그레이션** 전략을 정의한다.

## 0. 원칙 (실패 재발 방지)

- **Big-bang 금지**: Python 백엔드를 한 번에 교체하지 않는다.
- **병행 운영 우선**: 동일 API를 Python/Rust에서 동시에 검증한다.
- **계약(Contract) 고정 후 구현**: 기존 HTTP 계약(`/process`, `/search`, 에러 필드)부터 테스트로 고정한다.
- **관측성 선행**: 성능/에러/리소스 지표가 없으면 전환하지 않는다.
- **언제든 리버트 가능**: 라우팅 스위치(feature flag)로 즉시 Python 경로로 복귀 가능해야 한다.

---

## 1. 범위 정의 (무엇을 Rust로 옮길지)

### 1-1. 우선 전환 대상 (Low-risk)
- CPU 바운드이거나 독립 모듈 성격이 강한 영역
  - 검색 랭킹/스코어링 일부
  - 문서 메타데이터 전처리
  - 파일/경로 정규화 유틸리티 (계약 유지 전제)

### 1-2. 후순위 전환 대상 (High-risk)
- 워크플로우 오케스트레이션(`/process`), 큐/취소/진행상태 관리
- STT/교정/요약 모델 호출 및 외부 툴 체인 연계
- 업로드/레지스트리/히스토리의 쓰기 경로 전체

### 1-3. 비전환(당분간 유지)
- 프론트엔드(`frontend/src`)는 변경 최소화
- Python 기반 모델 연동은 Rust에서 래핑/호출 방식으로 병행 유지

## 9. 성능 이점 판단 (현재 코드베이스 리뷰 기준)

전제: 현재 백엔드는 `ThreadingHTTPServer` 기반 동기 처리이며, `/process`는 외부 모델 호출 비중이 큼. 검색 경로는 Python 루프 + 개별 벡터 파일 로딩(`np.load`) 비중이 큼.

### 9-1. 영역별 기대 효과 (보수적 추정)

- **검색(`/search`, `/similar`) CPU 구간만 Rust 전환**
  - 기대: p95 **1.5x ~ 4x 개선** (대용량 인덱스/캐시 미스 구간에서 유리)
  - 근거: 현재는 문서별 반복 루프, 파일 단위 로딩, 코사인 계산을 Python에서 직접 수행
- **HTTP 서버/라우팅 계층만 Rust(axum/actix) 전환**
  - 기대: 고동시성 QPS **1.3x ~ 2.5x 개선**
  - 단, 모델 추론 대기 시간이 지배적인 `/process` 체감은 제한적
- **`/process` 전체(오케스트레이션) Rust 전환**
  - Ollama API 사용 단계: 종단 처리시간 개선 **0% ~ 15%** 예상
  - 이후 llama.cpp 전환 단계: 종단 처리시간 개선 **5% ~ 25%** 가능
  - 이유: 병목이 Python 실행 자체보다 외부 추론(STT/LLM), 네트워크/프로세스 호출 오버헤드에 있음

### 9-2. Ollama → llama.cpp 전환을 고려한 핵심 판단

- **우선순위 1: Provider 호출 방식 최적화**
  - 현재 llama.cpp LLM provider는 요청마다 `subprocess.run()`으로 `llama-cli`를 직접 호출하므로, 이 구간은 Rust 전환보다 먼저 "지속 프로세스/API 서버 방식"으로 바꾸는 편이 효과가 큼.
- **우선순위 2: 검색 엔진/벡터 연산 모듈 Rust화**
  - 모델 provider 교체와 무관하게 지속 이득이 남는 영역이라 ROI가 높음.
- **우선순위 3: 오케스트레이터 Rust화는 Go/No-Go 뒤로**
  - 계약 호환/운영 복잡도 비용이 크고, 성능 이득은 상대적으로 작을 가능성이 높음.

### 9-3. 결론 (현 시점 권고)

- **전면 마이그레이션의 성능 ROI는 낮음**: 현재 구조에서는 모델 호출이 지배적이라 Python→Rust 전체 교체만으로 드라마틱한 개선을 기대하기 어려움.
- **부분 마이그레이션의 성능 ROI는 높음**: 검색·벡터 계산·고동시성 read API는 Rust 전환 가치가 충분함.
- **현실적 목표치 제안**
  - 1단계(검색/메타데이터): p95 30~60% 단축
  - 2단계(하이브리드 운영): 전체 API 에러율 유지(또는 감소) + 동일 하드웨어 처리량 1.5배
  - 3단계(`/process`): 10% 내외 개선이면 유지, 그 미만이면 Python 오케스트레이션 유지
