# 배포준비

코드는 배포라는 바다로 나가기 전, 관문을 통과해야 합니다. 이 스킬은 그 관문을 순서대로 닫아 잠그는 절차입니다.

## 운영 원칙(절대 규칙)

- 각 단계는 **PASS** 기준을 만족해야 다음 단계로 진행하십시오. **FAIL**이면 원인 해결 후 해당 단계부터 재수행하십시오.
- “새로 만드는 것”보다 **기존 관습/규약/코드 스타일/아키텍처**를 우선하십시오(레포의 전통을 따른다).
- 불명확한 요구가 있어도 작업을 멈추지 마십시오. 합리적 가정을 두고 진행하되, **가정/리스크를 명시**하십시오.
- 산출물은 항상 **짧고 단정한 체크리스트 + 근거(테스트/명령/파일 변경)** 로 제시하십시오.
- 안전: 데이터 파괴/대규모 리네임/스키마 변경/권한·인증 로직 변경은 특히 보수적으로 다루고, 롤백 경로를 반드시 포함하십시오.

## 출력 형식(매 단계 공통)

각 단계마다 아래 형태로 기록하십시오.

- **[Step N] 제목 — PASS/FAIL**
- 핵심 근거(최대 5줄)
- 변경/조치 목록(필요 시)
- 다음 단계로의 리스크/주의(있을 때만)

## 절차 (1–18)

### 1. 계획을 세우십시오
- 목표(What), 범위(In/Out), 성공 기준(DoD), 제약(시간/성능/호환성/보안)을 1회에 정리하십시오.
- 변경 예상 파일/모듈, 테스트 전략, 롤백 전략을 포함하십시오.
- PASS: “무엇을/왜/어떻게/어떻게 검증”이 한 장에 들어가면 PASS.

### 2. 계획을 검토하십시오
- 누락(엣지 케이스, 에러 처리, 마이그레이션, 호환성, 모니터링) 여부를 점검하십시오.
- PASS: 누락이 없거나, 누락을 보완한 수정 계획이 제시되면 PASS.

### 3. 검토한 것이 맞는지 다시 검토하십시오
- Step 2의 검토가 **성공 기준(DoD)** 과 **비범위(Out)** 를 제대로 반영했는지 재확인하십시오.
- “가정이 사실이 아니면 무엇이 깨지는가”를 3개 이내로 명시하십시오.
- PASS: 검토의 검토 결과가 계획에 반영되면 PASS.

### 4. 계획이 과도하지 않은지 검토하십시오
- YAGNI/단순성 관점에서 불필요한 구조·추상화·범위 확장 요소를 제거하십시오.
- PASS: “지금 필요한 최소 변경”으로 압축되면 PASS.

### 5. 구현하십시오
- 레포의 기존 패턴(레이어링, 네이밍, 에러 처리, 로깅, 타입/인터페이스)을 따르십시오.
- 변화는 작게 나누고, 변경 이유가 코드에 드러나게 하십시오.
- PASS: 컴파일/빌드 가능 상태를 유지하며 구현 완료.

### 6. 구현이 목적에 맞는지 검토하십시오
- 성공 기준(DoD) 항목별로 충족 여부를 체크하십시오.
- PASS: DoD가 전부 충족(또는 합리적 보완)되면 PASS.

### 7. 잠재적 버그/크리티컬 이슈/보안 문제를 검토하십시오
- 입력 검증, 인증/인가, 인젝션, 경로/파일, 직렬화, 경쟁 상태, 리소스 누수, 비밀값 노출을 점검하십시오.
- 의존성/서드파티 변경이 있으면 보안/라이선스 리스크를 확인하십시오.
- PASS: 고위험 이슈가 0개이거나 모두 완화되면 PASS.

### 8. 개선한 내용들에 문제(회귀)가 없는지 검토하십시오
- 기존 동작과의 호환/회귀를 점검하십시오(특히 API/DB/CLI/UX).
- 테스트 추가 또는 수정이 필요하면 수행하십시오.
- PASS: 회귀가 없거나, 발견된 회귀가 모두 해결되면 PASS.

### 9. 매우 큰 함수/파일이 있다면 적절한 크기로 나누십시오
- 과도한 책임/긴 함수/거대 파일은 분할하십시오.
- PASS: “단일 책임”이 읽히는 단위로 정리되면 PASS.

### 10. 기존 코드와 통합/재사용할 수 있는 부분을 검토하십시오
- 중복 유틸/도우미/도메인 로직이 있으면 재사용으로 치환하십시오.
- PASS: 중복이 제거되고, 결합이 자연스러우면 PASS.

### 11. 사이드 이펙트가 없는지 확인하십시오
- 성능(핫패스), 캐시, 트랜잭션, 이벤트/큐, 전역 상태, 설정 플래그, 로깅/메트릭 영향을 점검하십시오.
- PASS: 부작용이 없거나, 문서화/완화/테스트로 통제되면 PASS.

### 12. 전체 변경 사항을 다시 한 번 검토하십시오
- diff를 처음 보는 리뷰어 관점으로 읽으십시오.
- PASS: “이 변경이 왜 필요한지”가 diff만으로도 납득되면 PASS.

### 13. 구현 과정에서 불필요해진 코드를 정리하십시오
- 죽은 코드/주석, 임시 플래그, 사용되지 않는 함수/파일, 디버그 로그를 제거하십시오.
- PASS: 잔재가 남지 않으면 PASS.

### 14. 코드 품질이 충분히 높은지 검토하십시오
- 레포 표준(포맷/린트/타입체크/테스트/CI)에 맞추어 실행 또는 적어도 동일 수준으로 정렬하십시오.
- PASS: 로컬/CI 기준에서 실패 요소가 없으면 PASS.

### 15. 사용자의 사용 흐름에서 문제는 없는지 확인하십시오
- “사용자 시나리오” 1~3개를 실제 흐름으로 따라가며 확인하십시오(입력→처리→결과/오류).
- PASS: 주요 흐름이 막힘 없이 동작하면 PASS.

### 16. 검토 중 발견된 문제의 관련 부분을 끝까지 파고들어 재검토하십시오
- 이슈가 발견되면 “근본 원인 → 영향 범위 → 재발 방지(테스트/가드)” 순서로 처리하십시오.
- PASS: 임시 봉합이 아니라, 원인과 영향 범위가 닫히면 PASS.

### 17. 이대로 배포해도 될 퀄리티인지 최종 판정하십시오
- 최종 체크리스트:
  - DoD 충족
  - 테스트/린트/빌드 기준 충족
  - 보안 고위험 0
  - 회귀 0
  - 문서/변경 로그(필요 시) 반영
  - 롤백/마이그레이션 경로 명시
- PASS: “READY” 판정 가능하면 PASS. 아니면 “NOT READY + 블로커”로 명시하십시오.

### 18. 커밋하고 PR을 작성하십시오
- 레포의 커밋 관습(Conventional Commits 등)이 있으면 그대로 따르십시오(최근 커밋 히스토리 참고).
- 커밋은 가능하면 논리 단위로 나누십시오(기능/테스트/리팩터/문서).
- PR 초안에 반드시 포함:
  - 요약(무엇)
  - 배경/문제(왜)
  - 변경점(어떻게)
  - 테스트 방법/증거
  - 리스크와 롤백
  - 영향 범위(배포/마이그레이션/호환성)
