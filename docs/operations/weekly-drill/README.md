# 운영 점검 정례화 정책 (Weekly Drill Policy)

이 문서는 WBS 7.4 운영 점검 정례화의 **주기/역할/합격 기준/완료 조건**을 고정합니다.
점검 절차의 세부 내용은 `docs/operations-runbook-scenarios.md`를 기준 절차로 따릅니다.

## 1. 점검 주기 및 역할 (7.4.1)

### 주기

| 구분 | 주기 | 비고 |
|------|------|------|
| 기본 점검 | **주 1회** | 매주 월요일 점검 윈도우 권장 |
| 안정화 구간 완화 | **격주 1회** | 릴리스 안정화 확인 후 리뷰어 승인 시 허용 |
| 시나리오 A(장애 주입) | **최소 월 1회** | 기본 점검 회차 내 포함 |
| 시나리오 B(복구 검증) | **최소 월 1회** | 기본 점검 회차 내 포함 |
| 시나리오 C(부하/배압) | **최소 주 1회** | 매 점검 회차에 포함 |

### 역할

| 역할 | 책임 |
|------|------|
| **운영 담당(Operator)** | 시나리오 실행, 증적 수집, 결과 문서 초안 작성 |
| **리뷰어(Reviewer)** | PASS/FAIL 판정, 액션 아이템 승인, 격주 완화 승인 |

- 회차마다 운영 담당과 리뷰어를 결과 문서에 명시합니다.
- On-call 순환과 연동할 수 있으나, 최소 1인은 서비스 도메인 지식 보유자여야 합니다.

### 산출물

- 회차별 결과 문서: `docs/operations/weekly-drill/<YYYY-MM-DD>.md`
- 파일명 날짜는 점검 실행일 기준입니다.
- 결과 문서에는 `docs/operations-runbook-scenarios.md` 섹션 7-2의 필수 필드를 모두 포함합니다.

### 4주 확정 점검 일정 (2026-03)

| 주차 | 점검일 | 포함 시나리오 | 비고 |
|------|--------|----------------|------|
| 1주차 | 2026-03-02 | A, C | 장애 주입 기준선 확인 |
| 2주차 | 2026-03-09 | B, C | B 시나리오 FAIL 및 액션 등록 |
| 3주차 | 2026-03-16 | B, C | 전회 FAIL 액션 재검증 PASS |
| 4주차 | 2026-03-30 | A, B, C | 월간 빈도 충족 및 완료 판정 |

## 2. 시나리오 A — 장애 주입 합격 기준 (7.4.2)

- **수행 빈도**: 최소 월 1회
- **PASS 조건**:
  1. 장애 주입 후 `/readyz`가 `503 degraded`로 전이됨이 관측된다.
  2. 조치 완료 시점부터 **10분 이내** `/readyz`가 `200 ready`로 복귀한다.
  3. 복귀 후 장애 엔진의 신규 job이 정상 상태 전이(`queued -> running -> completed|failed`)를 재개한다.
- **FAIL 조건**: 위 조건 중 하나라도 미충족 시 FAIL 판정 후 액션 아이템 등록.

## 3. 시나리오 B — 복구 검증 합격 기준 (7.4.3)

- **수행 빈도**: 최소 월 1회
- **PASS 조건**:
  1. 복구 이후 `GET /jobs/{id}` 신규 요청이 정상 상태 전이(`queued -> running -> completed|failed`)를 재개한다.
  2. 복구 후 **30분 내** 미처리 stuck job이 0건이다.
  3. `/readyz`가 `200 ready` 상태를 유지한다.
- **FAIL 조건**: stuck job이 30분 내 해소되지 않거나 상태 전이가 재개되지 않으면 FAIL.

## 4. 시나리오 C — 부하/배압 합격 기준 (7.4.4)

- **수행 빈도**: 최소 주 1회
- **PASS 조건**:
  1. 부하 구간에서 `429` 응답이 발생할 때 `reason=queue_full|engine_full` 라벨이 관측된다.
  2. `/metrics`에서 `rejections(engine, reason)` 카운트가 reason별로 구분 기록된다.
  3. 부하 해제 후 **15분 이내** `/readyz`가 `200 ready`로 복귀한다.
  4. 부하 해제 후 queue_depth가 정상 수렴한다.
- **FAIL 조건**: reason 라벨 미분리, 또는 15분 내 ready 미복귀 시 FAIL.

## 5. 완료 조건 체크리스트 (7.4.5)

WBS 7.4를 완료로 판정하려면 아래 **모든 조건**을 충족해야 합니다.

- [x] 최근 4회(최소 1개월) 점검 결과가 `docs/operations/weekly-drill/`에 누적되어 있다.
- [x] 시나리오 A/B/C 각각의 최소 수행 빈도를 충족한다.
- [x] 회차별 PASS/FAIL 및 근거 지표(ready 복귀 시간, 429 reason 관측)가 기록되어 있다.
- [x] 미해결 액션 아이템이 0건이거나, 모든 액션에 책임자/기한이 지정되어 있다.

> 현재 상태: 2026-03-02/03-09/03-16/03-30 4회 점검 누적 완료. 2026-03-30 기준 WBS 7.4.5 완료 판정.

## 6. 계약 드리프트 주간 점검 항목 (신규 품질 게이트)

OpenAPI/API 계약 드리프트를 조기 탐지하기 위해, 매 주간 점검 회차에서 아래 항목을 **필수 확인**합니다.

- [ ] 계약 드리프트 기준 엔드포인트 세트를 `/healthz`, `/readyz`, `/metrics`, `POST /jobs`, `GET /jobs/{job_id}`로 고정하고 구현/OpenAPI에 동일 적용되는지 확인
- [ ] 구현 라우트 집합과 OpenAPI path 집합의 차이가 없는지 확인
- [ ] 구현 파라미터(path/query)와 OpenAPI 파라미터 정의가 1:1 매핑되는지 확인
- [ ] 상태 enum 7종(`queued|running|completed|failed|timeout|canceled|rejected`)이 구현/문서/OpenAPI 간 완전 일치하는지 확인
- [ ] 불일치가 발생하면 회차 결과를 FAIL로 판정하고 액션 아이템(책임자/기한) 등록
- [ ] CI 정적 계약 점검 결과(필수 path/param 존재 체크) 링크 또는 로그 요약 첨부
- [ ] CI 정적 계약 점검 스크립트 산출물 링크/경로(`artifacts/contracts/<run-id>/contract-drift-report.json` 등)를 회차 문서에 명시

> 운영 담당은 점검 결과 문서(`YYYY-MM-DD.md`)에 계약 드리프트 점검 결과(PASS/FAIL + 근거)를 명시합니다.
> WBS 1.2 재완료 판정 시에는 `docs/openapi-wbs-1.2-recompletion-gate.md` 체크리스트를 동일 기준으로 적용합니다.

## 7. 진행 현황 기록 규칙

- 누적 진행 현황(회차 수, 시나리오 빈도, 액션 잔여 상태)은 `docs/operations/weekly-drill/STATUS.md`에 집계합니다.
- 회차 문서(`YYYY-MM-DD.md`)가 추가되면 같은 커밋에서 `STATUS.md`의 표/체크리스트를 함께 갱신합니다.
- `STATUS.md`는 **완료 판정 근거 인덱스** 역할만 하며, 원본 증적은 각 회차 문서와 `/metrics` 스냅샷 링크를 기준으로 합니다.
