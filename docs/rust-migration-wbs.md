# Rust 신규 백엔드 구축 WBS (Work Breakdown Structure)

이 문서는 **기존 Python 백엔드(`sttEngine/*`)를 점진 이관하는 방식이 아니라**,
`deprecated` 대상으로 분리된 레거시를 유지한 채 **Rust 신규 백엔드를 별도 구축**하는 실행 계획입니다.

## 1) 전략 요약

- 전략: Migration(부분 이관) → **Greenfield Build(신규 구축)**
- 원칙:
  - 레거시(`sttEngine/*`)는 유지보수/긴급 수정만 수행
  - 신규 기능은 Rust 백엔드에만 구현
  - API 계약은 호환 우선이되, 필요 시 버전 명시(v2/v3)
- 목표: 운영 리스크를 줄이면서 신규 아키텍처를 독립 출시

---

## 2) 단계별 WBS

### 0. 거버넌스/범위 확정 (1주)

| WBS ID | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 0.1 | 레거시/신규 경계 정의 | 범위 ADR | `sttEngine/*` = deprecated, Rust = active 합의 |
| 0.2 | API 정책 수립 | API 호환 정책 문서 | 호환/비호환 기준 및 버전 정책 확정 |
| 0.3 | 릴리즈 정책 수립 | 출시/롤백 정책 | 병행 운영 및 롤백 절차 승인 |

### 1. 기반 구축 (2주)

| WBS ID | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 1.1 | Rust backend 저장소 구조 생성 | `rust-backend/` 스캐폴드 | 빌드/실행 가능한 최소 서버 |
| 1.2 | 공통 모듈 설계 | config/logging/error 모듈 | 표준 에러 응답 포맷 확정 |
| 1.3 | 관측성 기본 탑재 | health/metrics/tracing | 운영 대시보드 연동 가능 |
| 1.4 | CI 파이프라인 구성 | Rust lint/test/build workflow | PR 자동 검증 동작 |

### 2. API 재구현 (4~6주)

| WBS ID | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 2.1 | read API 1차 구현 | `/health`, `/models`, `/history` | 계약 테스트 통과 |
| 2.2 | 검색 API 구현 | `/search`, `/similar` | 정렬/필터/오류 응답 호환 |
| 2.3 | 업로드/메타 API 구현 | `/upload`, `/tasks`, `/progress` | E2E 시나리오 통과 |
| 2.4 | WebSocket 이벤트 설계/구현 | 진행률 이벤트 채널 | 프론트 실시간 진행 표시 가능 |
| 2.5 | OpenAPI 문서화 | `docs/openapi.yaml` 갱신안 | 프론트/QA 합의 완료 |

### 3. 워크플로우/엔진 통합 (3~5주)

| WBS ID | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 3.1 | `/process` 오케스트레이션 설계 | 상태 전이 다이어그램 | 취소/재시도/실패 규약 확정 |
| 3.2 | Provider 추상화 재구축 | STT/LLM/Embedding 인터페이스 | provider 교체 가능한 구조 |
| 3.3 | 실패 규약 구현 | `error_code/retryable/failed_step` | 기존 프론트 오류 카드 호환 |
| 3.4 | 파일/DB 경로 호환 | `DB/...` alias 정책 반영 | 레거시 데이터 읽기 호환 |

### 4. 전환/출시 (2~3주)

| WBS ID | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| 4.1 | 병행 운영 환경 구성 | blue/green 또는 canary 구성 | 트래픽 분할 가능 |
| 4.2 | 성능/안정성 검증 | 부하/장애 리포트 | SLO 충족 |
| 4.3 | 트래픽 전환 | 점진 전환 실행 기록 | 목표 비율 전환 성공 |
| 4.4 | 레거시 역할 축소 | deprecation 운영 가이드 | 신규 개발 경로 완전 분리 |

## 3) 공통 작업 트랙

### A. 품질/테스트

- 계약 테스트: Python legacy vs Rust 응답 비교
- 회귀 테스트: 핵심 플로우 자동화
- 성능 테스트: p50/p95, 처리량, 에러율 고정 시나리오 추적

### B. 문서/운영

- `README.md`: 사용자 실행/배포 기준 업데이트
- `AGENTS.md` + `CLAUDE.md` + `GEMINI.md`: 에이전트 작업 기준 동기화
- 운영 문서: 장애 대응, 롤백, 온콜 체크리스트

## 4) 마일스톤 (예시 12주)

| 주차 | 마일스톤 | 핵심 산출물 |
|---|---|---|
| 1주 | M0 | 범위/정책 ADR |
| 2~3주 | M1 | Rust 백엔드 기반 + CI |
| 4~7주 | M2 | 주요 API 재구현 + 계약 테스트 |
| 8~10주 | M3 | `/process` 및 provider 통합 |
| 11~12주 | M4 | 병행 운영 검증 및 전환 |

---

## 5) Definition of Done

- Rust 신규 백엔드가 핵심 API 및 워크플로우를 독립 제공
- 프론트 연동 기준 E2E 시나리오 통과
- 성능/SLO 목표치 충족
- 레거시는 `deprecated` 유지 모드로 전환되고 신규 기능 개발 대상에서 제외
- 문서(README/AGENTS/CLAUDE/GEMINI) 최신 상태 유지
